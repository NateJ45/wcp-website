# CLAUDE.md

Guidance for Claude Code (and any developer) working in this repo. Read this first.

## What this is

The **West Chester Preschool** website — a volunteer-run cooperative preschool site, migrated off Squarespace onto a self-hosted stack the board can edit themselves.

**Stack:** Astro 7 · Tailwind v4 · Sanity (headless CMS) · Cloudflare Workers. Node **≥ 22.12**.

The whole public site is a **Sanity page-builder**: non-technical volunteers log into the Studio and edit every page Squarespace-style (click-to-edit, add/reorder sections, build new pages) with no code changes. See [docs/PAGE_BUILDER.md](docs/PAGE_BUILDER.md).

## How to talk to Nathan (chat, code comments, commit messages)

Use ASD-STE100 Simplified Technical English in all chat responses to Nathan, in all code
comments that you write or change, and in all commit messages. The rules do not change the
site copy voice or the volunteer guide. Do not rewrite old comments only to change their
style. Keep the comment density the codebase already has — the rules change the sentences,
not how much you explain.

- Write short sentences. Use a maximum of 20 words in an instruction. Use a maximum of 25
  words in a description.
- Put one topic in each sentence. Put one instruction in each sentence.
- Use the active voice. Say who does what.
- Use the simple present tense where possible.
- Use one word for one meaning. Do not use synonyms for variety. Keep the same name for the
  same thing in the full conversation.
- Do not use noun clusters of more than three words. Break them apart.
- Use numbered lists for steps. Use bullet lists for facts.
- Define a technical term the first time you use it.
- Put a warning before the instruction it applies to, not after.

## Keep the docs in sync — on every change

**A change is not done until the docs describing it match reality.** Treat documentation as part of the change, not a follow-up. On every add / remove / modify — a feature, file, command, config, secret, gotcha, section type, or field — before you consider the work finished:

1. **Update the affected markdown.** Grep the docs for anything the change touches and fix it in the same commit: this file (`CLAUDE.md`), [`README.md`](../README.md), and everything in [`docs/`](docs/) (`PAGE_BUILDER.md`, `SANITY.md`, `FAMILY_HUB.md`, `FORMS.md`, `GOOGLE.md`, `TESTING.md`, `PENDING.md`, ...). New gotcha → add it to the Gotchas list. New command / secret / route → update the relevant section. Queued or stopgapped work → keep `docs/PENDING.md` current. (`docs/superpowers/` is the one exemption: historical snapshots, never synced.)
2. **Update the in-Studio volunteer guide** ([`src/sanity/guides/content.ts`](src/sanity/guides/content.ts)) **whenever the change alters what a volunteer sees or does** — a new/removed/renamed section type, a changed field or workflow, a new editing surface. This is the Help & Guide a non-technical board member reads; stale steps there are worse than none. (Purely internal changes — refactors, build config, this kind of stega fix — don't need a guide edit, but consciously decide that each time.)

The point: never leave stale docs that could mislead a later developer, AI, or staff member. If you changed it, the docs (and the guide, when volunteer-facing) change with it.

## The mental model: two content paths

Everything here makes sense once you hold these two paths apart:

|                | **Public marketing site**                            | **Family Hub** (`/family-hub/**`)                |
| -------------- | ---------------------------------------------------- | ------------------------------------------------ |
| Rendering      | **Static** — prerendered to HTML at build time       | **SSR** — server-rendered per request            |
| Who sees it    | Everyone                                             | Enrolled families only (password gate)           |
| Content source | Sanity, read at **build time**                       | Sanity, read at **request time** behind the gate |
| Reader client  | `src/lib/cms.ts` (build env token)                   | `src/lib/sanity.ts` (Worker runtime token)       |
| Updates when   | The site **rebuilds** (webhook on publish, ~1-2 min) | ~1 min (authenticated Sanity CDN)                |
| Docs           | [docs/PAGE_BUILDER.md](docs/PAGE_BUILDER.md)         | [docs/FAMILY_HUB.md](docs/FAMILY_HUB.md)         |

A third piece, the **Presentation preview** (`/preview/**`), is SSR + draft-aware (stega click-to-edit) and used only inside the Studio. It is `noindex` and never part of the static output.

## Conventions (follow these)

### Brand & content

- **Brand-lock is non-negotiable.** The page-builder gives volunteers _content_ control (what sections, what order, text, photos) but **zero design control** — no color/font/spacing/layout fields. Bands are limited to background `white|grey|cream|navy` + seam/compact booleans; images require alt; icons are a validated dropdown. Never add a design knob to a section schema. This is what keeps volunteer-built pages on-brand and avoids the "AI slop" look.
- **Copy voice (visitor-facing text only):** no em-dashes, no ellipses. Short, warm, parent-centered. Avoid AI-tell words (delve, leverage, robust, seamless, nurturing, "not just X, it's Y"). Internal docs and code comments are exempt.
- **Public design system = "Construction Paper" (Act II, approved 2026-07-18; brief in docs/superpowers/2026-07-18-public-2026-redesign-brief.md).** The rules that bind new public work: (1) **Display type never hyphenates** — the public layer sets `hyphens: none` on headings, and CMS-fed heading text goes through `displayTitleHtml()` (`src/lib/typography.ts`, unit-tested) which escapes then glues hyphenated compounds ≤14 chars ("Pre-K", "co-op") in nowrap spans; render new heading paths through it, don't interpolate raw title strings. (2) **Tour-first conversion doctrine is code-owned:** every CMS hero renders primary CTA "Schedule a Tour" → the tour form (PageHero synthesizes it; the first stored non-tour action survives demoted to ghost), with the proof line ("4.8 on Google · our tuition is public") underneath, plus `SpotsLine.astro` under it (a hidden line that hydrates HONEST live availability — "Spots open in Twos and Threes for fall" — from `/api/availability` via `src/scripts/availability.ts`; it only ever reveals true good news, never fake urgency), and `TourPill.astro` (BaseLayout public branch) floats the mobile tour CTA between hero and footer. `BackToTop.astro` floats bottom-LEFT on BOTH surfaces (public + hub; TourPill owns bottom-right). Don't add competing primary CTAs to hero or chrome. (3) **Dark-mode paper doctrine:** prints, parent notes, and tape are PHYSICAL OBJECTS — light paper in BOTH themes, fixed inks from `.wcp-note-paper`'s palette (never theme tokens inside them; the `-ink` trap); UI cards stay theme-reactive. (4) Public artifact primitives live in globals' scrapbook layer: `.wcp-taped-chip` (the eyebrow's replacement), `.wcp-annotation` (Great Vibes margin notes — the signature loader watches for it), `.wcp-press` (pressable CTA physics), `.wcp-proof-line`.

### Accessibility & motion

- **Accessibility is a hard gate.** Sections must keep their heading order (`SectionHeader as="h2"`, card `h3`) and `aria-labelledby` wiring, or the Lighthouse a11y score drops below 100 and CI fails. The Playwright a11y test runs axe's **default** rule set (not a wcag-only filter) on purpose — it catches the best-practice rules Lighthouse also checks. **Target is WCAG 2.2 AA** (audited 2026-07-14, public + gated hub, both themes): the default axe set already enforces the one machine-checkable 2.2 rule, `target-size` (SC 2.5.8) — don't narrow the test to `.withTags([...])` or you drop that coverage. SC 2.4.11 (Focus Not Obscured) is handled by the root `scroll-padding` in `globals.css` — the site has sticky top chrome (mobile header, desktop compact bar, hub topbar) and a fixed phone tab bar, so any new sticky/fixed chrome must stay within that padding budget (~4.5rem top). The other new 2.2 criteria (2.5.7 Dragging — the directory map has zoom buttons + a full List alternative; 3.2.6 Consistent Help; 3.3.7 Redundant Entry; 3.3.8 Accessible Auth — the login field allows paste + `autocomplete="current-password"`) are structural and pass; keep them that way.
- **Motion is opt-in and reduced-motion-safe.** The motion toolkit lives in `globals.css`: the `data-reveal` scroll system (variants `up`/`fade`/`left`/`right`/`scale`/`blur`, stagger via `--reveal-delay`) plus reusable classes `wcp-lift`, `wcp-pop` (icon pop on `.group` hover), `wcp-nudge`, `wcp-sheen` (CTA sheen), `wcp-underline`, `wcp-float`, `wcp-progress-fill` (HubProgress bar grows in from the left, the linear sibling of HubRing's dash sweep), `wcp-glow-drift` (transform-only ambient breathing for a decorative `wcp-glow` — never touches the per-theme glow opacity, so contrast is unchanged), `wcp-shimmer` (one light sweep across a loading skeleton — put it on the clipping container), `wcp-breathe` (a slow scale-only pulse on the ONE hero figure per view — `HubStat breathe`, never opacity so contrast is untouched), `wcp-twinkle` (a small sparkle scale+opacity, staggered via `--twinkle-delay`; capped at a few at a time — around the greeting sun, flanking the hub topbar's Super Helper CTA, or on ClassHelperRow's "Your class" badge(s) — never a field), and `wcp-glow-pulse` (a breathing box-shadow ring for a pill that should read as "notice me" at rest, not just on hover — the hub topbar's amber Super Helper CTA and the "Your class" badge once a family picks their class(es); reserve for a genuinely singular moment per element, more reads as noise). The Family Hub also has an ambient background layer — `.wcp-hub-wash` (three fixed, transform-only brand glows drifting under every card, rendered once in BaseLayout's hub branch; roams the mid-field so it never doubles the baked `.wcp-hub-canvas` corner washes). Everything that MOVES is gated behind `@media (prefers-reduced-motion: no-preference)`, so reduced-motion users get a still page — keep it that way, and never put motion on the LCP hero heading (it would delay first paint). **Never CONTINUOUSLY animate a large `filter: blur()` layer** (esp. a `position: fixed` one): a big animated blur is a mobile GPU trap — costly to raster, and a fixed animated layer forces some phones to repaint everything overlapping it every frame (scroll stutter + cards visibly flashing). The hub's ambient `.wcp-hub-wash` drift and `wcp-glow-drift` gate their animation behind `@media (prefers-reduced-motion: no-preference) and (pointer: fine)` so touch devices get the blur STATIC (painted once), and keep `will-change` inside that gate so the static layer is never needlessly promoted (2026-07-17 mobile regression). Hover lifts on interactive Tailwind must always pair with `motion-reduce:hover:translate-y-0`. **Public motion vocabulary (Act II) is four moves — settle, crayon scroll-draw, hover-straighten, press — with exponential ease-out curves only** (the public layer overrides `.wcp-pop`'s elastic bezier; don't add bounce/spring curves to public surfaces), and reveal staggers wrap within the visible group (`i % n`, see PhotoGallery), never accumulate across a whole collection. One-shot celebration bursts use the canvas confetti in [`src/scripts/confetti.ts`](src/scripts/confetti.ts) (`celebrate()`); [`src/scripts/hub-celebrate.ts`](src/scripts/hub-celebrate.ts) fires it once per browser for an EARNED milestone marked `data-celebrate` (+ `data-celebrate-once="<id>"`, id encoding the goal so a new goal re-earns it) — wired to a family hitting its co-op-hours goal and the school crossing its fundraising goal. Milestone confetti fires on the achievement, never on a passive page load with no accomplishment behind it.

### The hub app surface

- **Each class owns a brand color — use the helper, don't hardcode.** Twos = amber, Threes = green, Pre-K AM = orange, Pre-K PM = sky (matches the Sanity `class.color` field). [`src/lib/class-colors.ts`](src/lib/class-colors.ts) is the single source of truth: `classColor(slug)` gives the color, `classStyles(slug)` gives ready-made AA-safe Tailwind class sets (`badge` = white on a theme-stable dark fill for photo overlays, `chip`/`text`/`iconChip` for labels, `border`/`dot` for accents). The strings are full literals so Tailwind's JIT generates them — never build `bg-${color}`. Applied on the directory class overlay, the hub class pages (`ClassHubBody`), tuition cards, and the hub class nav cards. When you show or mention a specific class, tint it with this helper.
- **The hub's app layer is device-local, never account-based.** The my-classes picker (`wcp-my-classes`, a JSON array — MULTI-select, families span classes), "new since last visit" (`wcp-updates-seen`), the remembered family name for the co-op-hours lookup (`wcp-family-name`), theme, rail collapse, and note-modal dismissals all live in localStorage — progressive enhancement over a fully working no-JS page. The canvas texture (`.wcp-hub-canvas` grain + doodle tile + three soft brand washes baked into the same background, all under the white cards; direct grey Sections go transparent over it), the fixed WCP emblem watermark (`.wcp-hub-emblem` bottom-right, over a page-grey `.wcp-hub-emblem-plate` disc that hides the doodles inside the mark), the `wcp-glow-*` washes, the phone tab bar (`HubTabBar`), and the ⌘K palette (`HubSearch` + gated `/family-hub/api/search-index`, which indexes the WORDS and image alt text inside every section, not just page titles — shaping in `src/lib/hub-search-index.ts`, and the Directory is deliberately excluded because that response is cached and those entries are PII) are the app chrome — see docs/FAMILY_HUB.md "The app layer".
- **Hub pages are one app surface — reuse the hub primitives.** Every `/family-hub/*` page uses `HubShell` `bare` (no navy band) → `<Section bg="grey">` → **`HubPageHeader`** (owns the page `h1#hub-page-title`) → content in **`HubCard`** (the single card primitive: plain / titled / `as="a"` link / `as="li"`; carries the **`.hub-note`** paper-note look from globals.css — graph-paper texture + a faint rotating brand-colour SURFACE tint via `--note-accent` (color lives in the tinted surface + the icon chip, NOT a top/left strip — a card strip is an AI-slop tell), and a `postit` prop for a warm sticky-note fill — shared with `HomeWidgetCard`; the pinned/tilted look is reserved for the community photo wall, not these cards) → `HubProgress` for bars → `HubEmptyState` for empty data (pass a `spot` for a friendly brand illustration from **`HubSpot`** — a small starter spot-illustration set in the WCP hand: navy line + soft brand fills + the sun/cloud motif, isolated behind one component + a `spot` name so commissioned art can swap in later without touching call sites; decorative → aria-hidden) → `SectionRenderer` as a top-level sibling for Board-added sections. Data gets expressed through the 2026-07-14 kit: **`HubStat`** (KPI number + label + optional delta; opt-in `countUp` ticks a plain-number value up from 0 on scroll-in — reduced-motion-safe, formatting in the unit-tested `src/lib/count-format.ts`), **`HubRing`** (progress ring, fill sweeps in), **`HubSpark`** (aria-hidden sparkline, honest series only, draws itself in on load), **`HubPill`** (the ONE status vocabulary — extend it in the component, never improvise a pill), **`HubFilterChip`** (the ONE filter/segmented-nav chip — the Calendar/Directory filters; extend it, don't re-improvise the chip class string), **`HubTable`** (table that stacks to cards below `md` via `data-th`). The chrome is `HubTopBar` (desktop sticky bar: search affordance, what's-new bell, quick actions — native `<details data-hub-menu>` + `hub-menus.ts`/`hub-fresh.ts` behavior) and the shell holds still across hub navigations via `view-transition-name`s in globals.css. Icon-chip convention: neutral `bg-sky/15 text-sky-ink`; class-specific `classStyles(slug).iconChip`; semantic (money→green, health→orange, celebration→amber) only where it carries meaning. Don't hand-roll card classes — route through `HubCard`. The faint topic-icon "stamp" in a card's bottom-right corner is **`HubWatermark`** (the ONE watermark implementation): it sits behind content via `-z-10`, so the card root needs `relative isolate overflow-hidden`. It's applied broadly: `HomeWidgetCard` and `HubCard` (auto-on for a titled icon card — `icon` + `title`; `watermark={false}` opts out) render it by default, the custom hero cards (greeting, store, social wall, Super Helper, Handbook) drop it in, and `cardGridSection` cards get it **only inside the hub** — `HubSectionedBody` passes `cardWatermark` down `SectionRenderer` → `CardGridSection` → `FeatureCard`, so the SAME card grids stay clean on the public marketing site. Extend/reuse `HubWatermark` rather than re-inlining the corner-icon span. The reskinned inner pages are covered by `npm run test:hub` (axe light+dark + 320px, per route).

### Architecture habits

- **Navigation: native cross-document View Transitions + Speculation Rules (NO ClientRouter).** The 2026-07 performance pass removed Astro's `<ClientRouter />`: every navigation is a real document load, which is what lets Chrome/Edge fully PRERENDER the next public page on hover (the `speculationrules` script in BaseLayout — public pages only; SSR surfaces are excluded so prerenders never burn Worker time or hit gated routes). The cross-fade comes from the `@view-transition` rule in `globals.css` (Chrome+Safari; reduced-motion users get an instant swap). Client scripts still wire the DOM through `onPageLoad(fn)` from [`src/scripts/_page-load.ts`](src/scripts/_page-load.ts) — same API, now "once per document" (DOMContentLoaded or immediate) — and `onBeforeSwap` maps to `pagehide`. Two rules for new scripts: (1) keep using `onPageLoad`, never raw top-level DOM wiring; (2) anything that must wait for a REAL visitor (heavy downloads, autoplay, analytics pings) must check `document.prerendering` and defer to `prerenderingchange` — see [`src/scripts/hero-video.ts`](src/scripts/hero-video.ts), which otherwise would download ~9MB inside hidden prerendered pages. The scroll-reveal ([`src/scripts/reveal.ts`](src/scripts/reveal.ts)) reveals on-screen elements via a geometry check so first paint never waits on IntersectionObserver.
- **Match the surrounding code.** Components are heavily commented with the _why_; keep that density. Tailwind v4 (CSS-first config in `src/styles/globals.css`), no `tailwind.config.js`.

### Secrets & privacy

- **Secrets never get committed.** `SANITY_TOKEN` lives in `.env` (build reads) and `.dev.vars` (Worker runtime) — both gitignored. `FAMILY_HUB_PASSWORD` is a Cloudflare secret. The Fourthwall store creds — `FOURTHWALL_STOREFRONT_TOKEN` (read-only) and `FOURTHWALL_API_USER`/`FOURTHWALL_API_PASSWORD` (**super-admin** basic auth) — are Worker runtime secrets too (`.dev.vars` + `wrangler secret put`; typed in `src/env.d.ts`, consumed only by `src/lib/fourthwall.ts`). Server-side only; the Open API creds can read all orders incl. customer PII, so `getMerchStats()` (gross sales line) and `getStoreProfit()` (net-profit "Store Sales" card on /family-hub/fundraising) read **sums only** and never surface order/customer data. See [docs/SANITY.md](docs/SANITY.md) and [.dev.vars.example](.dev.vars.example).
- **Share-by-link Google URLs never get committed either.** This repo is public. The class photo albums, helper-schedule Sheets, the budget Sheet, the calendar feed, and the Drive/Canva documents are all "anyone with the link" resources — the URL _is_ the access control. They are Board-editable in Sanity and must live only there; the code fallbacks (`src/data/hub/live-links.ts`, `documents.ts`) ship with empty values on purpose. Never paste a share link back into a tracked file. If one is exposed, rotate it in Google (new link / restrict access), not just remove it from source.
- **Visitor tracking is consent-gated, per category.** Two optional categories: **Analytics** (GA4, `PUBLIC_GA_ID`) and **Advertising** (Google Ads tag `PUBLIC_GADS_ID` + Meta Pixel `PUBLIC_META_PIXEL_ID`). Setting ANY of those env vars renders the cookie-consent card (`CookieConsent.astro` — toggle rows appear only for configured categories, no dead switches) and `src/scripts/consent.ts` injects only the granted categories, through Partytown (`forward: ['dataLayer.push','fbq']` in astro.config for future main-thread conversion events). Decision in `localStorage` `wcp-consent` (versioned — bump `CONSENT_VERSION` in `src/lib/consent-state.ts` when the inventory grows a category, which re-asks); footer "Cookie choices" reopens the card with toggles reflecting the stored state. Everything else is consent-exempt by design and must stay that way: the Cloudflare beacon is cookieless, video/map embeds are click-to-load on the nocookie host (`src/lib/embeds.ts`), and theme/hub-login storage is essential. If you ever add a script that sets a third-party cookie, wire it into a consent category, never load it unconditionally. Tests: `tests/consent.spec.ts` (the OTHER Playwright suites run with a pre-stored decision via the config-level `storageState`, so the card never overlays them; the webServer build sets fake ids for all three trackers).

## Gotchas (these have each cost real time)

### Rendering & deploy

- **A plain class in `globals.css` BEATS every Tailwind utility — unlayered CSS outranks `@layer utilities` regardless of source order or specificity.** Tailwind v4 emits its utilities inside `@layer utilities`; everything hand-written in globals.css is UNLAYERED, and unlayered rules win against any layer. So `.wcp-sheen { position: relative }` silently overrode `class="fixed"` on TourPill: the mobile "Schedule a Tour" CTA rendered `position: relative` and sat ~10,000px down the page under the footer, on every page, for everyone EXCEPT reduced-motion visitors (the sheen block is motion-gated, so only they got a working pill). It shipped that way and was found live 2026-07-19. When a custom class sets a property a utility also owns (`position`, `display`, `overflow`, ...), either scope it tightly or re-assert the utility (`.wcp-sheen.fixed { position: fixed }`, as globals now does). Anything positioned by a utility is worth a live check.
- **SSR pages cannot resize images — never use `astro:assets <Image>` for chrome on `prerender=false` routes.** The Cloudflare adapter's image optimization is compile-time only; on SSR pages `/_image` passes the ORIGINAL file through, which served the 9000x6000 (4.1MB) logo into a 38px hub-topbar slot (Lighthouse, 2026-07-14). SSR surfaces use committed pre-sized assets (`src/assets/brand/*-sm.webp`, generated with sharp) and a plain `<img>` with width/height. Related: a font used only inside a lazy UI (the note modals' Great Vibes signature) must load via the **FontFace API** at open time (`note-modal.ts`) — both static and dynamic CSS imports get hoisted into render-blocking page stylesheets by Vite.
- **`wrangler deploy` alone 404s every sub-route.** This is a hybrid static+SSR build; deploy with the adapter-generated config: `wrangler deploy -c dist/server/wrangler.json` (baked into `npm run deploy` and the Deploy workflow).
- **CI/Lighthouse builds need `SANITY_TOKEN`.** Since pages are CMS-driven, `getStaticPaths()` reads them from Sanity at build time — a tokenless build emits an empty site. All three workflows pass `secrets.SANITY_TOKEN`.

### Sanity & the Studio

- **`/studio` is blank under `npm run dev`.** The project folder path contains spaces (`West Chester Preschool Website`), which breaks Vite's dev-time Studio module loading. **Dev-only** — the deployed `/studio` is fine. To edit locally, use the deployed `/studio` or `npx sanity dev`. There is intentionally **one** Studio — the embedded `/studio` (always current because it rebuilds on every deploy); we do **not** run a separate hosted `*.sanity.studio`, which drifts out of date. Don't `npx sanity deploy`. See [docs/SANITY.md](docs/SANITY.md).
- **Slug is a string + regex, not Sanity's `slug` type.** Sanity's slugify strips the slashes that `classes/twos` needs.
- **Never compare a stega-encoded string in logic.** In the `/preview` path, stega encodes ~1KB of invisible marker characters into every string so click-to-edit works, so `tone === 'navy'` is `false` on an encoded value and the component picks the wrong branch (this once rendered the navy CTA as cream in preview only). Dropdown/enum fields that drive rendering are excluded from stega via the `filter` in [`src/lib/cms-preview.ts`](src/lib/cms-preview.ts) — **add any new logic-driving enum field to that `NON_STEGA_FIELDS` list.** Display strings stay encoded (that is the point).
- **Custom Studio document-view panes must NOT call `useFormValue` — read the `document.displayed` prop instead.** `useFormValue` needs a `FormValueProvider` that is present in the Structure editor but NOT when a view (`S.view.component`) is mounted inside the **Presentation** tool, so it throws `useFormValue must be used within a FormValueProvider`; the thrown error trips the panel's error boundary, which freezes the Presentation panel AND kills the comlink that refreshes the preview iframe (looks like "editing broke the preview / it won't update until I reload"). Every `UserViewComponent` receives `{ document: { displayed, draft, published, historical }, documentId, schemaType }` — `document.displayed` is the live draft-merged doc and updates as you type (see `SeoPreviewPane.tsx`, which this bit 2026-07-13). Input components (rendered inside the form) may use `useFormValue`; standalone panes/tools/actions may not.

### Build output & testing

- **Trailing slash:** static `output` + directory format means `/about` → 307 → `/about/` → 200. Expected, not a bug.
- **Hero videos are gitignored** (`public/hero/*.mp4|webm`, belong in R2/Sanity), so they 404 on a clean build and the site degrades to the poster image. The link-check and tests skip them.
- **Windows-only:** local `lhci autorun` can exit 1 on an `EPERM` temp-cleanup crash even when the audit passed. Linux CI is the real Lighthouse gate.
- **Site search and share cards need a build.** The `postbuild` npm hook runs Pagefind over `dist/client` (so `/search` returns nothing under `astro dev`) and then `scripts/generate-og.mjs`, which renders the `/og/*.jpg` share cards — a real classroom photo (deterministic pick from the public A Day gallery, cropped by the Sanity CDN) under a satori/resvg overlay (scrim + logo + title), composited to JPEG by sharp — for every page/post that references one. OG generation is a postbuild **script** on purpose: resvg's native `.node` binary can't go through the Cloudflare adapter's bundler (an in-app endpoint fails the build), and deriving the card list from the built HTML means `check:links` proves none are missing. A third postbuild step, `scripts/rehost-instagram.mjs`, then downloads every baked `cdninstagram.com` image into `dist/client/ig/` and rewrites the HTML to same-origin URLs — the signed IG CDN links expire in days, so hotlinking them in static HTML rots between rebuilds (per-image failures leave the original URL and never fail the build). **Anything that deploys must run `npm run build` (which fires `postbuild`), never bare `astro build`** — the deploy script once used `astro build` directly and shipped a dist with no search index and no share cards (found live 2026-07-13; both `npm run deploy` and CI now go through `npm run build`).
- **A stale `astro dev` on port 4321 silently invalidates `npm test`.** The Playwright webServer (`npm run build && npm run serve:dist`, port 4321, fake tracker env so the consent card renders) has `reuseExistingServer` locally — if a daemonized `astro dev` (see the gotcha above: it always detaches on this stack) is still holding 4321, the suite runs against THAT dev server instead: consent tests fail "card not found", and every other result is meaningless (dev can serve 500s that pass reflow). Before trusting a local run, check the port (`netstat -ano | findstr :4321`) and kill the stale PID (`taskkill //F //PID <pid>`; `pkill` does not exist in this Git Bash). Bit the redesign branch 2026-07-18: 8 consent "failures" that were really a 3-day-old orphaned dev server.
- **The static a11y/reflow/smoke suites can't reach the gated hub** — they serve the static `dist/client`, and `/family-hub/*` is SSR-only (excluded on purpose, see `tests/routes.ts`). Hub shell coverage lives in `npm run test:hub` (`playwright.hub.config.ts`), a separate config. It boots with `npm run build && npm run preview` (wrangler), **not** `astro dev`: on this Astro 7 + Cloudflare stack, `astro dev` always daemonizes to a detached background process and the launching command exits immediately, which Playwright's `webServer` reads as a startup failure even though the server is actually up.

### Hub runtime

- **`src/middleware.ts` is the ONLY thing protecting family PII — never add a bypass flag to it.** No hub page or endpoint does its own auth check, so that one file guards 23 pages (directory with real names/addresses/phones, the children's photo wall, health details), 4 API endpoints, and the `/_server-islands/*` renders. It shipped with a `const HUB_OPEN = true` preview switch that was never flipped back, leaving all of it readable by anyone; found and closed 2026-07-19. The switch is deleted, not set to `false`. A new hub surface is protected the moment it lives under `/family-hub` **and** sets `prerender = false` — miss either and it is silently public, so add it to the route lists in `tests/hub-gate.spec.ts` when you build it.
- **The hub session stores a password FINGERPRINT, not a `true` flag** (`src/lib/hub-auth.ts`). The middleware re-derives `sha256("wcp-family-hub:v1:" + FAMILY_HUB_PASSWORD)` per request and compares, which is what makes rotating the secret sign everyone out — a boolean would have survived rotation forever and kept departed families inside. It **fails closed**: a blank/missing secret locks the hub rather than opening it. Two consequences to remember: any code asking "is this visitor signed in?" must go through `isFamilyAuthed()` and never test the session value for truthiness (a stale fingerprint is a truthy string — `login.astro` doing that would bounce families between the login page and the hub forever), and `session.cookie.maxAge` in `astro.config.mjs` is load-bearing (Astro's default has none, making it a browser-session cookie that forgets families on restart).
- **Adding a CMS read to a SHARED section component silently breaks the hub.** Several `sections/*` bridges render on BOTH the static public site and the SSR hub (`HubSectionedBody` whitelists `classCardsSection`, `splitMediaSection`, and others). On the public site a `cmsFetch` is a harmless build-time read; on the hub it becomes a per-request external fetch, which violates the hub speed contract and, with Sanity quota-blocked, timed out `/family-hub` entirely (30s `page.goto` failures across the hub suite, 2026-07-19). Gate any new read behind a prop that only public callers set — `SectionRenderer` passes `pageSlug` for public pages only, which is the available signal (see `showFees` on `ClassCardsSection`). Before adding a fetch to anything in `sections/`, check `HubSectionedBody`'s type list.
- **A resting `transform` and `data-reveal` cannot live on the same element.** The reveal system animates `transform`, so it overwrites any resting `rotate()`/`scale()` on that node and clears it once the reveal finishes. Every tilted paper object (`.wcp-chooser-card`, `.wcp-photo-print`) therefore splits across two elements: the outer one carries `data-reveal` and the tilt ANGLE as a custom property (custom properties inherit), the inner one carries the actual `transform: rotate(var(--tilt))`. Symptom when you get it wrong is silent — everything renders flat with no error. Related: `.wcp-print`'s alternating tilt uses `nth-of-type`, which collapses to a single angle when each card is the only element of its type in its own wrapper, so set the angle inline from the loop index instead.
- **WebKit will not send a `Secure` cookie over `http://localhost`; Chromium will.** `astro preview` serves the PRODUCTION build (so Astro sets `secure: true`) over plain http, which meant the hub suites' `webkit-iphone` project silently landed on the login page for every test while `chromium` passed — 17 failures whose only symptom was a missing `h1#hub-page-title`. `playwright.hub.config.ts` sets `WCP_INSECURE_COOKIES=1` for its webServer, which `astro.config.mjs` reads to drop the flag for that build only. Never set that var for a real deploy. If hub tests fail on one browser only, check the cookie before the markup.
- **`npm run test:hub` now needs a working `.dev.vars` password.** The gate is closed in preview, so a `setup` project signs in and saves `tests/.auth/family.json` (gitignored) for the content suites; the `gate` project deliberately runs with no session. If the hub suites suddenly all fail at sign-in, check `FAMILY_HUB_PASSWORD` in `.dev.vars` before suspecting the tests.
- **Client scripts loaded once for both hub chrome pieces.** The hub drawer (`src/scripts/hub-drawer.ts`) and theme toggle (`src/scripts/theme.ts`) are imported once from `BaseLayout`'s hub branch, not per-component — `HubRail` is rendered twice (desktop rail + the drawer's contents), and `theme.ts` already re-queries all `[data-theme-toggle]` instances on click, so this stays in sync without extra wiring. Both use `onPageLoad`/`onBeforeSwap`.
- **Server islands render hub content — the middleware gates `/_server-islands/*` too.** The hub home's Google-backed widgets are `server:defer` islands (instant shell, skeleton → streamed widget). Their endpoints live OUTSIDE `/family-hub`, so `src/middleware.ts` applies the same auth check to `/_server-islands/*` (401, not a login redirect). If a PUBLIC page ever gains a server island, that check must learn to tell them apart. No-JS visitors keep the skeleton fallbacks for those three widgets — an accepted trade. **Island content streams in AFTER the per-document scripts have scanned the DOM.** `data-reveal` is safe (reveal.ts has a MutationObserver for late insertions — added after the 2026-07 live regression where the three widgets sat at opacity 0), but every OTHER script hook (`data-countdown`, `data-countup`, forms, embeds, ...) is a one-shot scan and would never wire up inside an island. Don't put scripted content in a server island without giving its script the same MutationObserver treatment — and remember Playwright's `toBeVisible()` counts `opacity:0` as visible, so test the computed style like hub-home.spec.ts's regression test does.

### Colors, dates & cross-browser

- **Dark-mode elevation is a lighter SURFACE, not a shadow.** All 107 `shadow-*` utilities are black-based, and a black shadow cannot lift a card off an already-dark page — the diagnosis is written at the hub rail in `BaseLayout.astro`. Raised cards take `--color-surface-raised` in dark (one tonal step above `--color-surface`), which is the Material/Atlassian answer: pair the surface step with the shadow. **Do not "simplify" this by raising `--color-surface` itself.** That was tried once and reverted, because `.hub-note--postit` mixes amber INTO that token and the lifted composite pushed muted text under AA. `theme-tokens.test.ts` asserts both that the raised token actually separates and that the postit still mixes against the unraised one.
- **Never style focus with `--color-navy`, and never `focus:outline-none` without a replacement.** Navy is deliberately never re-declared in `.dark` (it drives the theme-stable navy bands), so a navy focus ring measures ~1.1-1.6:1 on dark surfaces. Eight forms shipped with `focus:outline-none focus:border-navy focus:ring-navy/30`, which suppressed the correct global ring and replaced it with an invisible one: keyboard focus did not exist in dark mode, on a green build with Lighthouse at 100. The global `:focus-visible` rule in `globals.css` already draws a theme-reactive 3px `--color-sky-ink` outline — the right move is to leave it alone. Form field classes now live in one place, `src/lib/field-classes.ts`; use those constants rather than pasting the string again (it had been copied into eight files, which is why one bad rule broke all of them).
- **Neither axe nor Lighthouse can see focus-indicator or custom-border contrast.** They have no rule for it, and `a11y-dark.spec.ts`'s sweep audits the resting DOM, so nothing was ever focused. That blind spot hid five real WCAG failures. Two gates now cover it: `src/lib/theme-tokens.test.ts` reads the real token values out of `globals.css` and checks the load-bearing pairs in both themes (milliseconds, catches it at authoring time), and `a11y-dark.spec.ts` has a focus pass asserting every field actually gets an indicator. When you add a colour token that marks a UI component or a state, add its pair to the token test.
- **`--color-*-ink` tokens are for text on a dark PAGE, not for a fill inside a fixed-chrome island.** In dark mode `globals.css` redefines `--color-orange-ink` (and the other ink tokens) to alias the bright tier, because bright colors read fine as text on a dark page. The hub rail's navy chrome doesn't change with the site theme, so its active-link fill hardcodes the ink hex (`#a85300`) instead of the token — using the var there would silently break contrast in dark mode. See the comment in `HubRail.astro`.
- **Colored `-ink` text on a soft color tint fails AA in DARK mode — the #1 trap when building hub cards.** `text-sky-ink` on `bg-sky/15`, `text-orange-ink` on `bg-amber/25`, etc.: in dark mode the `-ink` token flips bright AND the tint darkens over the dark surface, so contrast drops to ~4:1 or worse (a text pill that's fine in light mode). Rules: (1) soft-tint backgrounds are safe **only** behind an `aria-hidden` icon; the **label text stays neutral** (`text-heading`/`text-ink`/`text-ink-muted`). (2) Keep tinted chips inside white `HubCard`s, never directly on the `bg-grey` canvas (tint-over-grey is darker still). (3) `classStyles(slug).text` (an `-ink` color as text on a WHITE card, e.g. a price) is fine — that's verified AA in both themes; the failure mode is specifically colored-text-on-colored-tint. All hub inner pages are axe-checked in light AND dark by `npm run test:hub`, which catches these.
- **Greeting/date logic on the hub home must use Eastern wall-clock time, never raw `Date` methods.** The Cloudflare Workers runtime's `Date` is UTC with no local timezone data, so `getHours()`/`getDate()` produce the wrong "Good morning/afternoon/evening" (or the wrong day) for a chunk of the day. Always go through `toLocaleString(..., { timeZone: 'America/New_York' })` instead — see the working pattern in `HubGreeting.astro`. The pure date math (greeting hour, days-until, school-year percent, short-date formatting) lives in `src/lib/hub-dashboard-dates.ts` with Vitest coverage for the NaN/divide-by-zero/UTC-boundary edge cases — extend that module and its tests rather than inlining new date math back into the `.astro` components.
- **Date-only event strings ("YYYY-MM-DD") must be anchored to NOON UTC before timezone-formatting.** `new Date('2026-07-20')` is UTC midnight, which formats as July 19 in Eastern time — all-day events would show a day early. `src/lib/hub-calendar.ts`'s `eventDate()` does `new Date(iso + 'T12:00:00Z')` for date-only strings; use it, don't parse event dates by hand.
- **Hide-by-default + reveal-via-`:has()` must gate the HIDE behind `@supports selector(:has(*))`** (and JS-driven reveals must scope their hidden state to `.js`). An unconditional `display:none`/`0fr` whose only undo is a `:has()` rule leaves content PERMANENTLY invisible for no-JS visitors and `:has()`-less browsers (Firefox ESR 115, Safari ≤15.3) — this bit the FAQ accordion (answers could never open) and the hub store card (empty product area), both fixed 2026-07-17. The reveal system (`.js [data-reveal]`) is the model to copy.
- **bfcache restores skip `onPageLoad`: anything torn down on `pagehide` must rebuild on `pageshow` with `persisted`.** A Back/Forward restore re-shows the old DOM without re-firing DOMContentLoaded, so observers/timers/maps cleared in `onBeforeSwap` stay dead and state computed at load goes stale. `reveal.ts`, `DirectoryMap.astro` (Leaflet), `countdown.ts`, and `hub-fresh.ts` all carry the `pageshow persisted` re-init now — copy that pattern in any new script with a pagehide teardown or load-time-computed UI state.
- **Two cross-browser traps fixed 2026-07-17, don't reintroduce:** (1) `position: sticky` never sticks inside an `overflow-hidden` ancestor — corner-rounding wrappers around sticky content must use `overflow-clip` (HubTable). (2) iOS Safari only synthesizes bubbling `click` events for taps on "clickable" targets, so document-level outside-tap dismissal must listen on `pointerdown`, not `click` (hub-menus.ts; the public nav dropdowns in nav.ts got the same fix 2026-07-17, regression-guarded by tests/public-interactions.spec.ts).
- **`color-scheme` is declared in `globals.css` (`:root` light / `.dark` dark) on purpose** — it opts the site out of Samsung Internet / Chrome-Android forced auto-darkening, which would otherwise invert the navy chrome and the theme-stable islands. Don't remove it, and keep it in sync if the theming model ever changes.

### External data & caching

- **The Google Sheets gviz endpoint returns JSONP-ish text, not JSON.** `.../gviz/tq?tqx=out:json` wraps the payload in `google.visualization.Query.setResponse(...)`; there is no plain-JSON mode. `src/lib/gsheets.ts` cuts the JSON out from between the outer parens — go through it (`getBudgetSnapshot`/`getFundraisers`/`getAvailability`), don't fetch sheets by hand. All live-data fetches carry an 8s `AbortSignal.timeout` and degrade to a designed empty state on any failure (hub widgets show their empty card; the public availability badges just stay hidden — they hydrate from `/api/availability`, a 5-min-cached SSR route, so a sheet edit never waits for a rebuild).
- **Hub SSR speed contract: external fetches must go through `src/lib/hub-cache.ts`.** The Apps Script calendar feed (1.5-3s/hit) and gviz sheets (0.5-1.5s) once ran on EVERY hub navigation — pages took 2-4s server-side. They're now `cached()` in TWO tiers (an in-isolate Map plus the **CACHE KV namespace**; the binding is optional and everything degrades to Map-only without it) with **stale-while-revalidate**: the calendar is 12h fresh + 24h serve-stale-and-refresh-in-background (it's set weeks ahead), and the gviz sheets carry a PER-TAB window matched to how often each changes: Budget 12h (changes ~monthly), Fundraising 6h (the default), Availability 1h (shifts during enrollment). Weather/AQI ride 8h windows and the store 24h. Within the swr window a visitor is NEVER blocked on the origin — the refresh rides `waitUntil` behind the response. **KV WRITE BUDGET (this bit us 2026-07-15):** every KV-backed cache REFRESH writes through to the CACHE KV namespace, and the free KV tier allows only ~1k writes/day account-wide. **Sanity BOARD_CONTENT_CACHE is now L1-ONLY (`kv: false`) and writes ZERO to KV** — it was the dominant writer (a hubPage key per page + the always-rendered topbar, on nearly every view), and Sanity's authenticated CDN (~100-300ms) is fast enough that the cross-isolate durability isn't worth a write; the L1 Map still absorbs repeat navigations. Only the genuinely-SLOW/rate-limited external origins keep L2 KV (calendar, gviz sheets, weather/AQI/alert, Fourthwall, IG). Don't drop those TTLs without checking KV analytics (`kvOperationsAdaptiveGroups` in the Cloudflare GraphQL API, grouped by `namespaceId`); and if you add a NEW external per-request fetch, give it `cached()` with a TTL, but only leave `kv` on (the default) when the origin is slow enough to need survival — a fast origin should pass `{ kv: false }`. Reads are cheap (100k/day); writes are the ceiling. The rule: **singletons cached L1-only, collections live** (updates/documents/roles/campaigns stay on the CDN so lists always feel fresh), **PII never cached at all** (directory entries, health details — those reads pass no `cache`, so family data never sits in the module Map or KV), **read-after-write stays `fresh: true`** (sign-ups). The hub Sanity client uses the **authenticated CDN** (`useCdn: true` — still token-gated, ~60s staleness). Never add a new per-request external fetch to a hub page without wrapping it; and read-after-write surfaces (the sign-ups page) must pass `{ fresh: true }` to `sanityFetch` or a family's just-submitted response looks lost. Mutation clients (contact/signup APIs) keep `useCdn: false`.
- **Cache the RAW reading, never the copy you derived from it — a shipped wording fix stays invisible otherwise.** `getAirQuality()` used to cache the whole rendered `{aqi, icon, line}` object, so when the "AQI 51-100 is Moderate, not Good" fix deployed, the hub kept showing the OLD line: a deploy recycles the isolate (L1 gone) but **L2 KV survives it**, so the first visitor after shipping read the pre-fix envelope straight back out, and inside the 8h fresh window nothing even triggered a refresh. It looked exactly like a failed deploy — the number had moved on (59) while the sentence hadn't (found 2026-07-18, after three green Deploy runs). Cache the number; call `describeAqi()` at read time and a copy edit is live on the next request. Where derived text genuinely must be cached (`hub-weather.ts` bakes `describe()`'s label/line into the 7-day array), the **key carries a version suffix** (`weather:west-chester-oh:week:v3`) and you must bump it in the same commit as any copy or shape change. Same rule for a shape change: `air-quality:...:v2` exists because old object-shaped envelopes would otherwise be read back where a number is expected and render `AQI [object Object]`. Pure tier/copy lookups belong in a unit test (`hub-air-quality.test.ts` pins the EPA boundaries — 51 is Moderate); stub the cache with `vi.mock('@/lib/hub-cache')` so `cloudflare:workers` never has to load.
